1. Summary

32 rows compared. runs-on is a cloud product. CRSP runs on your own PCs.

13910

runs-on better same CRSP better

  • runs-on wins on scale, isolation, sizing, cache, reliability and docs.
  • CRSP wins on small-scale cost, data at home, Windows and macOS hardware, console, CLI, updates and no lock-in.
  • Best idea to take: send overflow jobs to a cloud runner (G1).

5. Worked cost example

Assumptions: 10,000 minutes a month, 2-vCPU Linux. runs-on price from its README: $0.0009 a minute (US East spot) against $0.0060 hosted. Licence from €300 a year, taken as about $25 a month. CRSP runs on your own PCs, so no cloud bill; power and hardware not counted. The $0.002 a minute GitHub self-hosted fee is unconfirmed and would hit runs-on and CRSP alike.

6. Options and roadmap

G1 Overflow to the cloud. A: do nothing. B (recommended): let the fallback variable point at a cloud label such as runs-on. C: build an AWS provider (large).

G2 Metrics. A: nothing. B (recommended): read-only Prometheus /metrics. C: OpenTelemetry push.

G3 Quickstart. A: nothing. B (recommended): one page from the install guide. C: separate docs site.

G4 Job debug. A: nothing. B (recommended): keep a finished container a few minutes, offer a shell command. C: live SSH.
  • M1: G1 (B), G3, G2 (B).
  • M2: savings and uptime views (G6, G7), G4 (B).
  • M3: cache receiver (G5), package proxy (G8), VM per job (G10). These three already exist as specs.
