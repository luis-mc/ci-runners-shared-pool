CRSP342: caches and package proxy, design options

Rows V (CRSP272) and W (CRSP273): Actions cache receiver, repository mirror, registry mirror, warmth and wipe, and a package proxy for npm, PyPI, crates and apt.

Recommendation

Option 1 for row V. The receiver, mirrors and wipe already live in the controller process and the failure rules are fixed, so a dedicated holder (option 2) buys little until a pool is large.

Row W: native npm and PyPI proxies on the same hub (option 1). Spike apt-cacher-ng from option 3 for apt, and write a small native sparse-index proxy for crates, then decide. Do not take containers for npm and PyPI: the metadata rewriting is small and keeps one budget.

Estimate: about 17.5 days for V and the npm and PyPI part of W; apt and crates later, about 5 days after the spike.

What the code says (checked 27 Nov 2026 on main)

  • Row V is already part built. internal/lancache holds one content-addressed store with three namespaces (tools, packages, actions), machine-key checks, a byte cap with least-recently-used eviction, a TLS listener that binds one private address only, and a client that treats any failure as a miss and skips a failed holder for 30 s (caches R5.50).
  • internal/mirror is built: the repository mirror, warmth (0 to 100 per machine and repository), wipe with a plan, and the settings. The controller is the only holder today, using <data>/mirrors/{actions,git,registry}. The per-machine base next to the tool cache (R5.65) is not wired.
  • Not built for V: the settings route and console switches (R5.66, R5.71), the refresh timer and push webhook, the agent step that sets the repository rewrite, the receiver's LAN listener wiring, Put Block and protobuf bodies, the real @actions/cache contract test, and the scheduler reading warmth. The existing Caches tab already lists and wipes the holder rows.
  • The package proxy (row W) has only the stored namespace: it speaks no npm, PyPI, crates or apt wire format (R5.50, section 11). The seam is the agent's engine settings and per-ecosystem variables (npm_config_registry, PIP_INDEX_URL, Cargo source replacement, apt proxy).
  • Failure table (spec section 8) already fixes the rule for all options: a cache failure never fails a job (open), a digest mismatch is refused (closed), a wipe waits for running jobs.
  • Correction to the earlier run: its option 1 counted the receiver and mirrors as new work. About 40 percent of V exists, so V is about 11 days left. The earlier plan left out the contract test against the real @actions/cache package, which the spec makes a condition of shipping the receiver; it is in the estimate now.

The three options

Option 1: One hub in the controller, one budget

The controller process serves the receiver, mirrors, registry mirror and a native npm and PyPI proxy from one store with one byte budget. Runners are pointed at it by environment at start.

Design

  • Where: inside the controller, in internal/lancache beside the built receiver; the package proxy is a new handler on the same listener, one path prefix per ecosystem.
  • Storage and eviction: the base folder of R5.65, one pool-wide budget (default 60 GiB), least recently used first; the existing Wipe plan covers every kind.
  • Pointing runners: the agent writes npm_config_registry, PIP_INDEX_URL and the repository rewrite pairs into the runner environment at start; a change reaches only runners started after it (R5.66).
  • Failure: a down hub is a miss and a 30 s skip; npm and pip fall back to the real registry because the agent sets a fallback list, not a single address.
  • Security: machine key plus private-address bind; keys scoped by repository id; package tarballs checked against the upstream integrity hash before they are stored.

Trade-offs

  • Smallest change and one place to monitor.
  • The controller disk and network carry every cache; a busy pool can slow the controller.
  • A restart of the controller drops all caches for a moment (they fall back to GitHub).

Risks

  • Receiver protocol is unofficial: it ships only behind the contract test and turns itself off with a doctor line.
  • Writing npm and PyPI metadata rewriters ourselves is maintenance we own.

Console touch points

  • Caches tab of Images and caches: four cards (Actions, repository mirrors, registry, packages), each with a switch and Wipe; one budget meter; warmth table by repository (R5.71).
  • Doctor: one line per cache that turned itself off.
  • CLI: crsp caches settings.

Option 2: Dedicated cache-holder machines

Any machine can be made a cache holder. The controller only records who holds what and tells runners where to go; data never passes through the controller.

Design

  • Where: the agent gets a holder role that runs the receiver, mirrors and package proxy on its own base folder (the sibling layout of R5.65).
  • Storage and eviction: a budget per holder, set on the holder; moving a cache starts it empty.
  • Pointing runners: the controller hands each runner the nearest holder at start; the client already keeps a holder list and skips a failed one.
  • Failure: a holder offline means misses and GitHub for the repositories it keeps; a second holder is the only redundancy.
  • Security: holder-to-runner calls use the machine key; a holder is added only by the owner, and the controller revokes it like a machine.

Trade-offs

  • The controller stays light and the cache can sit on a big disk (a NAS).
  • A new agent role, more states, and a placement question the owner must answer.
  • Needs a second machine to be worth it; one-machine pools gain nothing.

Risks

  • Largest build: agent role, holder election, a move that starts empty, and per-OS holder setup (Windows, macOS, Linux).
  • Holder placement across the LAN is untested on real machines; macOS has never run on a real Mac (R5.72).

Console touch points

  • Caches page becomes a holder table (machine, status, disk, what it keeps) with Make a machine a cache holder.
  • A note when a holder is offline, and a choice of what jobs do then.
  • Machines page gets a Holder badge.

Option 3: Checked off-the-shelf services

The package proxies are well-known programs (Verdaccio for npm, devpi for PyPI, apt-cacher-ng for apt) run as pinned containers that crsp starts, points runners at, watches and wipes. The Actions cache and mirrors stay native.

Design

  • Where: containers on the cache machine through the container backend crsp already has; each image pinned by digest and checked at each start, in the same way tools are checked (R5.19 to R5.22).
  • Storage and eviction: each program has its own folder and cap; crsp trims by its folder size, since the programs do not share a budget.
  • Pointing runners: same variables as option 1; apt gets an apt proxy file in the runner image.
  • Failure: container stopped means a doctor line, a restart attempt, and runners using the real registry meanwhile.
  • Security: containers on a private network, no outbound except to the registry hosts, versions updated only when the owner presses Update the checked versions.

Trade-offs

  • Apt and (partly) crates come for free and are well tested.
  • Needs a container engine on the cache machine; Windows and macOS holders need Docker Desktop.
  • Four programs, four storage models and four ways to wipe.

Risks

  • The pin must follow upstream security fixes; a stale pin is a risk we own.
  • No mature crates proxy; a thin native sparse-index proxy is still needed.
  • The container engine is a new dependency of the controller machine.

Console touch points

  • Caches page: table of cache programs (name, program and version, checked digest, status, size) with Start again and Update the checked versions.
  • Problem note when a program stops.
  • Actions cache and mirrors remain cards.
