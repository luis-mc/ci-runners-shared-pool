CRSP343: installers and release notes, design options

Row K (CRSP274): what is left for the MSI, pkg, deb and rpm installers, signing and notarization, and release notes.

Recommendation

Option 3 now, option 1 later. Release notes help every update from the next release on, need no money or lead time, and use a field the signed manifest can carry.

Start the certificate orders in parallel because their lead time is the long pole, then do option 1 when they arrive. Option 2 comes after option 1, since winget and Homebrew need a signed installer.

Estimate: about 5 days now, about 8 days plus certificate lead time later.

What the code says (checked 27 Nov 2026 on main)

  • Row Y (CRSP267) is built: agent auto-update one machine at a time, rollout steps, placement and removal. The update path checks the SHA-256 of each download and its build provenance attestation inside crsp (R5.34), and a signed Ed25519 manifest where required (internal/update/manifest.go).
  • The installers exist for every system: MSI (WiX v5, x64 and arm64), pkg (macOS), deb and rpm (OPS1). They install the same files and services (R5.7).
  • Signing is ready and off. release.yml signs the MSI with signtool and the pkg with productsign only when the repository variable SIGNING_ENABLED is true (D58, R5.45). Not built: notarization of the pkg, any check of an installer signature by the updater or the install script, signing of deb and rpm, and the attestation check in the install script.
  • No package repository exists: no apt or yum repository, no Homebrew tap, no winget manifest. Install is by download and docs/guides/install.md.
  • Release notes: GitHub's generated notes plus a fallback written from commit subjects (scripts/ci/release-notes-fallback.sh), with docs/guides/upgrade-notes.md placed on top. The update manifest has no notes field. The tray's What's new button opens the GitHub release page (internal/updatewindow). The console shows no notes.
  • Correction to the earlier run: notarization is a separate unbuilt step, not part of the existing signing switch, and a signed Windows installer is also what winget and SmartScreen need, so option 2 depends on option 1 for two of its four channels.

The three options

Option 1: Sign and notarize, show trust per installer

Get a Windows code-signing certificate and an Apple Developer ID, turn SIGNING_ENABLED on, add notarization, make the updater and install script check the signature, and show the trust of each installer in the console.

Design

  • Windows: Authenticode through the existing signtool step; a cloud signing service avoids holding a private key.
  • macOS: add notarytool submit and stapler to the existing productsign step.
  • Linux: sign deb and rpm with one release key (dpkg-sig style, rpm --addsign), public key in the repository and docs.
  • Updater and install script verify the signature next to SHA-256 and attestation; a bad signature is refused.
  • Console: a Trust column per installer on the Updates tab with the certificate expiry.

Trade-offs

  • The strongest answer to the warnings people see on first run.
  • Costs money and lead time; a certificate can expire and stop a release.

Risks

  • Certificate lead time: Apple 1 to 2 days, Windows 3 to 10 days for validation.
  • The release fails when a certificate is missing or expired (by design of R5.45).
  • Owner must hold and protect the keys.

Console touch points

  • Updates tab: Trust per installer table (system, file, trust, what the person sees).
  • Certificate card with expiry, and one button to turn signing on for the next release.
  • Doctor line 60 days before a certificate expires.

Option 2: Package repositories, with a switch for who updates

Publish an apt repository, a yum repository, a Homebrew tap and a winget manifest, and let the owner choose per machine whether crsp updates itself or the system package manager does.

Design

  • apt and yum repositories published from the release job, signed with a repository key.
  • Homebrew tap updated by the release; winget manifest submitted per release.
  • Who updates: the agent detects a package-managed install and switches self-update off; the console shows the choice and the reason.
  • Rollout steps still apply to crsp-managed machines only.

Trade-offs

  • People update with the tools they already trust.
  • Two update paths to keep consistent with the rollout and one-at-a-time rules (R5.18).

Risks

  • winget and Homebrew review can take days and reject unsigned installers, so two channels need option 1 first.
  • A package-managed machine can fall behind the controller; the console must say so.
  • Repository hosting and key rotation become a permanent duty.

Console touch points

  • Updates tab: Package channels table with version and status per channel.
  • Who updates this machine: a choice per machine, with a note about the Rollout page.
  • A note when a machine is behind and managed by the system.

Option 3: Release notes first, owner-facing notes in console and tray

Write a short owner-facing note for each release, carry it in the signed update manifest, and show it in the console and the tray before and after an update. Installers stay as they are.

Design

  • Source: an Owner note line in each change note (docs_fold change notes already exist) collected by the release job into the manifest's new notes field.
  • The manifest signature covers the notes, so the console shows only what the release signed.
  • Console: What is new on the Updates tab and a note after an update; the tray's What's new shows the same text instead of opening GitHub.
  • The release fails when a release has no owner note (same style as the existing notes fallback).

Trade-offs

  • Smallest, no certificates, helps every update at once.
  • Leaves the unsigned-installer warnings as they are for now.

Risks

  • Notes must be written in plain words; the release check only proves a note exists.
  • A manifest format change must stay readable by older agents (extra field, ignored).

Console touch points

  • Updates tab: a done note with Show what is new, a What is new section, and a table of earlier versions.
  • Tray: What's new opens the in-app text.
  • Rollout page links to the notes of the version a step moves to.
