Words used on this page
Runner: a program on a machine that takes one CI job at a time.
Slot: one place on a machine where a job may run.
Weight: how much of a machine a job takes. One unit is one slot's share.
Hook: a script GitHub runs on the runner just before a job's steps. crsp holds jobs there.
cgroup: a Linux feature that caps, and can count, the CPU and memory of a group of processes.
cargo: Rust's build tool and package manager.
Peak: the highest CPU or memory a job reached.
JIT runner: "just in time": a runner made for one job and removed after it.
Glob: a name pattern such as e2e-*.
Pool: the CPU and memory the owner lets crsp use on one machine (its pool size).
Class, allocation, ceiling: a runner's size (small, medium, large, xl) is the biggest job it may take. It owns no CPU of its own.
Requirement: the CPU and memory a job needs, from sizing.
Admit: crsp decides a job may start now, because the pool has room.
Label set: the runs-on labels of a job. GitHub gives a job to a runner that has all of them.
Webhook: a message GitHub sends to crsp when a job changes state.
Tool plan, store: the tools and versions a job needs, and the read-only folder where each version is kept once.

2. Sizing by what a job really does

Goal: no "heavy" from a name or a test-type tag. Use what the job did (measured) and what its code says it will do (scan and count).

What crsp already measures

  • Time, not resources: queue, slot, start, end, steps, job graph; forecast from the last 30 good runs, needs 5 (observability/spec.md:161-173, R5.35, R5.40, R5.41).
  • No CPU or memory per job. Idea 9 (CIX16) is "new agent sampling" (docs/project/content/ci-run-insights/03-exploration.html, 05-feature-options.html, docs/project/registry.json). No internal/insights code yet.
  • Scan reads manifests, not workflows (internal/stackscan/rules.go: "Workflows are not stack files").

Scan: 1 test × 1 project, 1 worker. Or 150 tests × 3 projects = 450 runs, 4 workers. The big job (4 CPU) exceeds the default 2-slot budget, so it runs alone (weight cut to the budget, R5.69): heavy. Sharding 4 ways (--shard with fullyParallel) cuts the time guess to about a quarter.

6.1 The model in one picture

Ceilings may add up to more than the pool (12 CPU of ceilings on an 8 CPU pool). That is safe, because a job starts only when the pool has its CPU and memory free.

The rules (decided by the owner, details are mine)
  1. A runner owns no CPUs or memory blocks. All runners of a machine share that machine's pool (the pool size of docs/features/machines/spec.md:267, R5.58).
  2. A runner has an allocation: its class (CPU and GiB). It is the biggest job it may take, a ceiling, not a reserved block.
  3. A job has a requirement (CPU and GiB) from sizing (section 2). With no history and no scan it is 1/1 (decision 8).
  4. Before a runner takes a job, two checks: the requirement is within the runner's ceiling, and the pool's free CPU and free memory both cover it.
  5. If both pass, the runner takes it. If not, the job waits, and a later job that fits may pass it.
  6. A job that waits long is protected from starvation (6.4).

Decided Enforcement: counting plus a hard memory cap per job; CPU is counted only. The pool container keeps the pool's CPU set and memory cap (internal/backend/container/container.go:78, cpuset.go:14); inside it, admission by counting decides who runs. A job's memory is capped at its runner's ceiling so one job cannot eat the others' share; CPU is not pinned or capped per runner.

Decided rule: reserve after 3 passes or 10 minutes, whichever comes first, then backfill.

10.1 How the listener works, as far as I know

  1. The crsp agent starts the listener of a registered runner (run.sh, a service, or the listener program directly).
  2. The listener creates a session with GitHub (a create-session call for the runner's pool and agent id). If an old session of the same runner still exists, GitHub refuses it (a conflict) and the listener retries until the old one expires. unverified
  3. It then long-polls for messages (about 50 seconds per call). While it polls, the runner shows as Idle (online).
  4. When a job matches, GitHub answers the poll with a job message.
  5. The listener starts a worker process that runs the job.
  6. The worker reports the job done; the listener goes back to polling at once.
  7. crsp asks the listener to stop (SIGINT or SIGTERM on Linux and macOS; a service stop on Windows).
  8. On a clean stop the listener deletes its session and exits; GitHub then shows Offline within seconds. After a hard kill there is no delete, and the runner stays "online" until the session times out, which I believe takes minutes. unverified
  9. An offline persistent runner stays registered. GitHub removes a runner that has not connected for more than 14 days (ephemeral: more than 1 day); documented, read in OPS65, not observed.

Top rows: what the runner list shows, with the listener always on and gated. Gated, the runner is Offline while it has nothing to do, Idle for the moment between start and assignment, Active during the job. The job waits queued in both cases until a listener is up; gated, crsp chooses when.
