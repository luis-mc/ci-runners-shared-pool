§ 1What and why

Two audits on 20 Nov 2026 showed that CI was slow for reasons no single run page shows. Jobs waited for runners for up to 4 h 53 min. Jobs ran serially when they could run in parallel. Tests slept on fixed timers, generated hundreds of cases, or had no time limit at all. crsp already sees every job it runs, so it is in the right place to find these problems for every project, and to keep finding them.

The owner's goals for this feature (20 Nov 2026):

  1. Guardrails that cannot be forgotten. Everything learned from the audits goes into the dev-standards plugins as enforcement: rules, hooks and guard scripts that run in Claude Code sessions, before a push and in CI. Memory notes are not enough.
  2. crsp audits all CI runs. It analyses each project's runs and the orchestration of all runs across projects. It recommends:
    • how to change the crsp setup to match the real demand (runners, labels, machine slots, images, caches, schedules);
    • how each project can improve its CI: run time, step order, wait time, repeated tests, tests that check nothing;
    • where each project stands against each dev-standards guardrail.
  3. Useful, not shelfware. Research best practices and similar products, test each idea against the crsp product concept, and build only what people will act on. A dashboard nobody opens is a cost in code and in the console.

This page grows as the exploration goes on over the next days. Each round adds findings, options and decisions.

The test guardrails being enforced

IDGuardrail
G1Every test runner has a per-test timeout: unit 10 s, integration 60 s, e2e 2 min. Never raise it to pass.
G2Every CI job sets timeout-minutes of 30 or less. Never raise it to pass.
G3No retries of failing tests in CI. Fix the test, or quarantine it with an issue draft.
G4No sleeps or open-ended wait loops. Use fake timers, or wait-for with a hard deadline.
G5Parametrize at most 20 cases per test unless a spec requires more. No new matrix axes without owner approval.
G6Mutation tests and property tests with many runs stay out of branch and PR CI.
G7Report the measured time of each new test.

Patterns across both projects

  1. Queueing beats test time. In both projects the longest delays were jobs waiting for a runner, not tests running. That is a pool sizing and scheduling problem, which is crsp's own job.
  2. Idle runners next to busy ones. comics-organizer's Windows runner sat idle for 51 min because of a needs chain, while the one Linux runner had a queue. A cross-project view would show this at once.
  3. After-merge work holds the shared runner. Mutation tests (81–156 min) and full nightly suites on master blocked PR jobs behind them. Scheduling that knows the job's purpose could keep PR work moving.
  4. Timeouts are missing or do not fire. Both projects have test runners with no per-test limit, and one MSI job ran 150 min past its own timeout. crsp sees the job's real duration and can flag this.
  5. Fixed waits and generated cases are the biggest test-time costs, and both are easy to detect statically.
  6. Per-test times are often missing. Playwright's line reporter and cargo test do not give them. A JUnit or JSON report from every runner would.

What research and practice say

  • Feedback time. DORA puts the upper limit for CI feedback at about 10 minutes.
  • Queues grow fast near full use. Wait time rises steeply between 80% and 95% utilisation (Kingman's formula). Applying it to runners is our own modelling.
  • Test selection. Meta's predictive test selection halved test cost and still caught over 95% of failures (ICSE 2019). It needs history and machine learning, which is too heavy for one owner.
  • Flaky tests. Rerunning until green can hide a real bug. A history rule (same commit, different result) detects flakes without rerunning.
  • What gets used. Google's static-analysis lessons (CACM 2018): put findings in the developer's workflow (code review), keep false positives near zero, and offer the fix, not only the finding. No direct evidence was found that CI dashboards get ignored, so treat that as a hypothesis.

What crsp already has

  • Every job's timeline: queued, slot taken, started, completed, wait reason, machine, runner, labels, matrix and the forecast made at the time (jobs, 90 days).
  • Steps from the workflow_job webhook (30 days), the needs graph per commit with the critical path, and daily rollups per repo and job type (400 days).
  • The slot log and wait reasons: no runner with the labels, load over budget, repository limit, quiet hours and others.
  • Places that already show it: Jobs charts, the run page (job graph, critical path), the job page (step waterfall), Pool size, Doctor findings, and registry recommendations that cannot be dismissed (registry R5.45).

Missing:

  • No test-level data. crsp reads no JUnit, logs or artifacts today. The observability spec (R5.38) says "never stored: logs". The owner explained on 20 Nov (D4) that this rule was meant to stop logs going to third parties: crsp may keep logs and test data on the owner's machines to improve its features. R6.7 (nothing leaves the machines) stays.
  • No reading of workflow or test files beyond needs.
  • No CPU or memory per job.
  • Pool size advice ignores job history.
  • No store for recommendations about the pool or projects.

dev-standards already writes a ci-run-times artifact and per-file test timings (ci-timings.json) in each project. crsp reads neither.

  • ci-fallback.yml uses 90 minutes.

Do not build

  • Predictive or coverage-based test selection: too heavy for one owner, and it risks skipping a regression.
  • Auto-retry or auto-quarantine that hides failures: it breaks G3.
  • A chart dashboard with no recommendations: GitHub already has one.
  • Automatic pool resizing or fix PRs merged without the owner: nothing is changed silently, and merging stays the owner's.
  • Mutation tests inside PR CI: they break G6.

§ 6Round 2: the dev-standards study (20 Nov)

dev-standards ran a read-only study of CI logs from 10 to 20 Nov: CI Test-Time Study (TC13).

  • It covers six repositories with CI: comics-organizer, ci-runners-shared-pool, moobable, lan-link, home-automation and dev-standards. shared-product-framework has no CI.
  • It ranks 20 causes by minutes saved per day and audits the seven guardrails in every repository.
  • Reviewed here on 20 Nov at 12:30 Lisbon. Every crsp claim that could be checked in the repository was checked.

Main finding: waiting, not testing

In five of the six repositories, tests take seconds to a few minutes. The hours go into waiting:

  • Queues: about 55 job-hours of pool queue in moobable, lan-link and home-automation, and about 620 min a day in comics-organizer.
  • The pool's job-start hold: the Set up runner step, p90 5.5 to 7 min, at most 30 min.
  • Housekeeping jobs that take a slot: artifact prune runs after every workflow, 38 times a day in comics-organizer, and one of them waited 421 min.

comics-organizer is the one exception: 4,581 Rust tests on 2 threads and one compile job, about 105 min per full run.

This confirms round 1 (queueing beats test time) with a much larger sample.

Note: the "pool" in the study is today's dev-standards pool (the machine slots and one job per repository at a time), not crsp. crsp replaces it. So every pool finding is a requirement crsp must meet, not a bug in crsp.

What it adds to the guardrail picture

  • G1 and G2 fail in all six repositories with CI, dev-standards included. Its templates ship no per-test timeout and no job timeout-minutes. That matches the template gaps in the guardrails section and is the strongest case for enforcing the guardrails in the templates and the guard (D1), not by memory.
  • dev-standards breaks G6 itself: gate mutation shards run on pull requests (spec-lint.yml:285-302). That also conflicts with its own DL-12 rule (--no-mutants on branch work).
  • G3 fails only in comics-organizer (Playwright retries: 1 and retry-crashed.ts). Production smoke there also retries automatically.
  • G4 sleeps are common everywhere except home-automation. Many are poll loops with deadlines of 30 to 90 s, which turn every failure into a long wait (study #4: 49 failures cost 91 min).

Requirements for crsp itself (it replaces the pool the study measured)

  • Parallel jobs per repository by measured headroom, not a fixed 1.
    • crsp already has repository_parallel_limit and the load budget (85% memory, 60% CPU).
    • The advice should say how many slots to allow, and why: "comics-organizer queued 620 min a day; a second Linux slot fits within the 85% budget".
    • Check this against the scheduling spec before the RUNS_ON switch.
  • Hold time is reported apart from run time.
    • On the old pool the job-start hold runs inside Set up runner, so GitHub counts it as run time. That makes slow tests look slow even when the time went into waiting.
    • crsp has slot_at, so its Jobs page and advice can always split wait, hold and run.
    • The study also asks that a hold be capped at about 2 min, and the job requeued with its reason, instead of a 30-min hold.
  • Housekeeping jobs never queue in front of real work. Prune, cleanup and a production smoke take a slot for under a minute but wait up to hours. Two options:
    • A small separate lane for jobs under a minute. The light runners were dropped in RELEASE-43; this would be a scheduling rule, not a runner type.
    • Advice to run them once a day on a schedule.
  • Superseded work is spotted. 3,109 job-min in 12 days in comics-organizer went to jobs of commits that were no longer the head. crsp sees head SHAs, so it can flag them, and, only if the owner turns it on, skip a queued job whose commit was replaced.

For dev-standards

  • Template fixes the guard would enforce:
    • timeout-minutes on every job in every template workflow, including the dev-standards check (dev-standards.yml) and the train-cleanup and artifact-prune workflows;
    • per-tier test timeouts for vitest, Playwright, Go, cargo or nextest, and dotnet;
    • a JSON test report and a ci-run-times artifact in every CI template.
  • The artifact-prune trigger: once a day on a schedule, not after every workflow (study #16). It is a dev-standards template.
  • Its own repository: mutation shards out of PR runs, and docs_check.py before a push (83 of its 218 failures came from that check).
  • These belong to dev-standards. The dev-standards study already lists them as its own tasks. crsp only reports them per repository (idea 6).

§ 8Baseline asks to compare with crsp's own advice

Owner decision of 20 Nov, 14:35: no pool changes on the old pool now. The order is:

  1. Move the projects to the crsp pool.
  2. Let them run there.
  3. Let CI run insights detect improvements and recommend actions.
  4. Compare those recommendations with the asks below, which people and studies made by hand before crsp could make them. A difference in either direction is a finding: crsp missed something, or the hand-made ask was wrong.
