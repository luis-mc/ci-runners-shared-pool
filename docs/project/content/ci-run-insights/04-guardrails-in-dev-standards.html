Goal: the seven guardrails hold in every project without anyone having to remember them. They should stop Claude in the session, stop a push, and fail CI.

Recommendation: extend luismc-delivery, put the numbers in STACKSPEC, no new plugin

LayerWhat it doesWhere
Every Claude sessionA rule file with the seven guardrails, each tagged with a DL check ID, delivered at session start.delivery/rules/test-guardrails.md, added to RULE_FILES in hook_session_start.py; new rows in DELIVERYSPEC
While Claude editsAn edit that raises a timeout or timeout-minutes, adds retries, adds a sleep or adds more than 20 cases is warned the first time and refused the second time in a turn.A new hook_test_edit.py, built like hook_design_edit.py
Before a push and in CIA guard script checks config (per-test and job timeouts, retries), scans added lines (sleeps, case counts, new matrix axes) and the workflows (mutation and property tests off PR CI). Existing breaches go in a known list that may only shrink.templates/shared/scripts/delivery/test_guardrails.py as a gate.json step (pre-push, branch gate, CI); test-guardrails.known.json checked by change_notes.py
New test times (G7)Reads the runner's report (vitest JSON, Playwright JSON, go test -json, cargo, dotnet TRX), prints each new test's time in the job summary and fails a test over its tier limit.test_guardrails.py times, next to ci_run_times.py
New projectsSTACKSPEC section 11.4 holds the limits. The track templates set them: vitest 10 / 60 s, Playwright 120 s, go -timeout, timeout-minutes: 30 on every CI job. The Mode 2 audit runs the guard.tech-stack-setup/references/invariants.md and assets/tooling/*

Why not a new plugin: delivery already has every layer: rules at session start, edit hooks, the installer that ships guard scripts to every project and track, and the shrink-only known-list check (the design-system kit, DL-92). A separate plugin would duplicate all of that and need its own installer and setup step.

Why not STACKSPEC alone: nothing runs after a project is generated, so a later edit that raises a timeout would not be caught.

Template gaps found while looking

  • The ts template's vitest.config.ts sets 60 s for the guard and integration projects and nothing for unit.
  • The Playwright template sets no test timeout.
  • None of the four ci.yml templates (ts, go, rust, dotnet) sets a job timeout-minutes.
  • ci-fallback.yml uses 90 minutes.
  • The dev-standards.yml checks job seems to have no limit (only its first 80 lines were read).
